## 一句話介紹

RetroVault 是一個給電玩/動漫收藏玩家用的個人資料庫 PWA（單一 HTML 檔前端 + Google Apps Script 後端 + 使用者自己的 Google 試算表資料庫），核心設計原則是**資料完全歸使用者所有**——App 只是操作介面，不經過任何第三方伺服器。

## 開工前一定要先做的事

## 技術架構（30 秒版本）

```
使用者瀏覽器（PWA）── HTTP ──▶ 使用者自己的 Google Apps Script ──▶ 使用者自己的 Google 試算表 + Drive
```

- 前端所有人共用同一份部署（GitHub Pages）
- 後端每個使用者各自部署一份、綁定自己的試算表——這是「資料互相獨立、互不可見」的關鍵設計，不要假設所有使用者共用同一個後端
- AI 辨識呼叫 Google Gemini，使用者自己的 API 金鑰存在瀏覽器本機，不經過中介伺服器
- 8 大收藏分類（遊戲/書籍/主機/週邊/原聲帶/動漫美術/公仔/數位下載版），其中 4 個有子類型細分，共 32 張工作表

## 已知踩坑（開發這個專案容易踩到的雷）

1. **`completeness`（品項完整度）不是簡單字串**——是逐組件（本體/外盒/說明書等，依分類不同）各自評級、序列化成字串存的複合欄位，「裸卡」是本體專屬選項不是獨立等級。曾經有過完全猜錯欄位格式重寫一次的教訓（v03.08→v03.09），改這個欄位前務必先讀 `COMP_COMPONENTS`／`serializeComp`／`parseComp`／`quickCompPreset()`。
2. **IGDB 後端回傳的是扁平化欄位**（`platform`/`developer`/`release_date` 直接是字串），不是 IGDB 原始 API 那種巢狀結構。`extractField('igdb',...)` 對照表如果照原始 API 格式寫會悄悄抓空（v02.146 修過）。
3. **`showForm()` 會呼叫 `hideAllSecs()`**，所以絕大部分建檔模式的觸發區塊在進表單後會自動隱藏，不太需要擔心「表單開著時使用者重新觸發辨識、資料被覆蓋」這種競態——但如果新增一個「表單開著時仍然可見」的觸發點（例如 AI 網頁查詢的貼上框），就要自己補上「只補空欄，不覆蓋」的保護。
4. **`URL.createObjectURL()` 用完要記得 `revokeObjectURL()`**——圖片辨識的縮圖預覽曾經漏了這個，長時間使用會緩慢洩漏記憶體（v03.05 修過）。
5. **GAS 邏輯異動要主動判斷是不是「實質變更」**，加 `LockService`這種「感覺只是加個保護」的異動也算數，要觸發版號重整規則，不要等部署完才想起來。
6. **批次相關的全域 `entry` 變數是共用情境物件**——`_batchResolveAll()`／`batchSaveAll()` 平行處理時，準備階段（碰到全域 `entry`）必須維持循序執行，只有真正耗時的網路請求才平行化，否則多個項目會互相搶用同一個全域變數、資料互相覆蓋。

## 目前已知但還沒處理的事項（供你評估要不要繼續）

- **⚠️ Apps Script 部署網址可能在手冊截圖裡部分曝光**——`docs/Photo/0004.jpg` 這張截圖看得到網址開頭 `https://script.google.com/macros/s/AKfycb...`（被輸入框截斷，沒看到完整版）。因為部署設定是「存取權＝所有人」，網址本身就是唯一的存取控制手段。當時建議使用者要嘛逐張檢查全部 `docs/Photo/` 截圖有沒有完整曝光、要嘛乾脆重新產生一個新部署換掉網址比較保險——**這件事截至目前沒有確認使用者是否已經處理**，如果使用者又提到這個話題，先確認狀態再繼續。
- **拍照辨識（`buildSYS`）跟 AI 補全（`aiKnowledgeFill`）用的是兩份不完全同步的欄位模板**——例如 `bonus_code_status` 只在 `AI_CAT_SPEC` 裡有列，`_SYS_GAME` 手調提示詞沒提到，代表純拍照辨識不會主動判斷 DLC 狀態，但事後觸發 AI 補全卻會。這不是 bug，是兩套機制天生的設計差異，但如果之後要讓兩邊完全同步，是一個可以做的優化方向。
- **v02.109 稽核提到的 14 個死掉的 DOM id**——當時記錄「還沒清理」，這次對話沒有再處理，如果要做通用性的程式碼清潔可以考慮撿回來看。
- **圖片欄位在不同畫面用了 7 種以上不同尺寸參數**（80/150/300/500/800/1000px 等）——之前評估過統一/精簡尺寸能減少快取碎片化，但風險較高（要逐一確認每個畫面實際需要多大的圖），暫緩。

## 開發時的工作方式（這個專案已經建立起來的協作習慣）

- **修改前先簡短說明要動哪些地方**；完成後回報改了什麼、產生了哪些檔案、做過哪些驗證、有沒有需要使用者手動處理的事項。
- **每個功能性改動都要有最小可執行檢查**：`node --check` 語法檢查是基本盤；邏輯異動要另外用 jsdom 建立實際會執行的測試環境驗證（這個對話大量使用這個模式：`mkWindow()` 建立模擬 DOM、直接呼叫真實函式、斷言實際行為，不是憑印象猜測）。
- **重大功能異動（不只是小 bug fix）建議先評估、列出方案，讓使用者確認方向再動手**，不要一次埋頭寫一大包程式碼才發現方向錯了。這個對話裡多次先「查證＋列表格＋給建議」再等使用者說「做」才動手，是目前雙方都適應的節奏。
- **版本推進務必依照協作規則.md 的規則走**：純前端改動只加小版號；GAS 有實質邏輯變更要主動判斷、觸發主版號歸零；子版號/debug 版有各自簡化流程。
- **部署流程固定套路**：改本機檔案 → 語法檢查 → jsdom 功能測試 → 用 `github_deploy.py` 一次 commit 推送（含 docs/ 檔案＋CHANGELOG）→ 用 GitHub Contents API 核對線上內容真的正確 → 等 GitHub Actions 建置完成確認 success。
